# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

QuantTrade is a full-stack trading strategy backtesting platform: a FastAPI backend (`BackEnd/`) and a React + Vite frontend (`FrontEnd/`). Users create projects, define trading strategies (via indicators + entry/exit rules, or sandboxed custom Python signal code — see Strategy definition & execution below), and run backtests against stored market data.

## Commands

### Backend (`BackEnd/`)
Dependencies are managed with [uv](https://docs.astral.sh/uv/) via `BackEnd/pyproject.toml`/`uv.lock` — there is no `requirements.txt` and no manually-created venv; `uv` creates and manages `BackEnd/.venv` itself from the lockfile.
```bash
cd BackEnd
uv sync          # creates .venv and installs pinned deps + dev group (pytest et al.)
uv run uvicorn app:app --reload
```
`uv add <package>`/`uv remove <package>` (run from `BackEnd/`) update both `pyproject.toml` and `uv.lock` together — edit dependency versions through these rather than hand-editing `pyproject.toml`, so the lockfile never drifts out of sync. Runtime deps live under `[project.dependencies]`; test-only deps (`pytest`, `pytest-asyncio`, `aiosqlite`) live in the `dev` group under `[dependency-groups]` — add new deps to whichever one matches, e.g. `uv add --dev <package>` for a test-only dep.

Alternatively, run the full stack (Postgres included) via `docker compose up` from the repo root — see `README.md`'s Docker Setup section. `BackEnd/Dockerfile` also uses `uv` (via the official `ghcr.io/astral-sh/uv` image, copied in as a static binary) and runs `uv sync --locked` at build time, so a dependency change needs `docker compose up --build` to take effect, same as before.

### Tests
```bash
cd BackEnd
uv run pytest tests/ -v
```
Must be run from `BackEnd/` (or with `BackEnd` on `PYTHONPATH`) — `tests/__init__.py` relies on pytest's rootdir-relative import mode to resolve `from services...` imports; running `pytest BackEnd/tests` from the repo root will fail to import. There is no `pytest.ini`/`conftest.py` pinning this.

Test coverage: `services/strategy_executor.py` (`tests/test_strategy_executor.py`) — indicator correctness, position sizing/costs, and metrics, all unit-tested with hand-verified expected values (no mocks, no DB). `tests/test_backtest_ownership.py` and `tests/test_strategy_ownership.py` cover the ownership-check async regression (see below) against a real async session, using an in-memory `sqlite+aiosqlite` engine (dev-only deps `pytest-asyncio`/`aiosqlite`, pinned in the `dev` group of `pyproject.toml`) rather than mocks — `pytest.ini` sets `asyncio_default_fixture_loop_scope = function`. `tests/test_data_upload.py`, `tests/test_data_historical.py`, and `tests/test_data_import.py` cover `routers/data.py` the same way. There is otherwise no test suite for routers/services that touch the database, and no frontend test suite.

**SQLite tests can hide Postgres-only bugs — verify dialect-sensitive fixes against real Postgres too.** `test_backtest_ownership.py::test_run_backtest_queries_market_data_with_datetime_not_raw_string` exists because SQLite's `DateTime` bind processor passes a raw Python `str` through unchanged (so `MarketData.date >= "2024-01-01"` "works" against SQLite), while Postgres/asyncpg binds it as `::VARCHAR` and rejects `timestamp >= varchar` outright — a bug the SQLite-only suite could never catch by actually hitting Postgres. That test instead asserts on the *type* of the value SQLAlchemy binds into the compiled query (via `stmt.compile(compile_kwargs={"literal_binds": False}).params`), which is dialect-independent and catches the same class of bug. When a fix depends on Postgres-specific type strictness (as opposed to ORM-relationship behavior, which SQLite reproduces fine per the ownership-check regression below), don't trust a SQLite-only green suite — run `docker compose up` and exercise the real endpoint against the `postgres` service before calling it fixed.

### Environment
Copy `BackEnd/.env.example` to `BackEnd/.env` and set `SECRET_KEY` (JWT signing) and `ALGORITHM` (e.g. `HS256`); both are read via `os.getenv` in `services/auth_service.py` with no defaults, so the app will error on auth routes if unset. `CORS_ORIGINS` is a comma-separated list consumed in `app.py`. `DATABASE_URL` is read from the environment in `database/connection.py` (via `os.getenv`, falling back to `postgresql+asyncpg://postgres:postgres@localhost/quanttrade` if unset) — set it in `.env` to point at a different Postgres instance. The Docker Compose stack (`docker-compose.yml`) overrides it to point at the `postgres` service. `ALPHA_VANTAGE_API_KEY` is optional — read via `os.getenv` in `routers/data.py`, falls back to Alpha Vantage's public `"demo"` key (which only serves a handful of sample symbols, e.g. `IBM`) if unset; can also be overridden per-request via the `api_key` query param on `POST /api/data/import/{ticker}`.

## Architecture

### Backend request flow
`app.py` wires global middleware (in registration order, so the *last*-added middleware runs *first* per Starlette's stack): CORS → per-request DB session middleware (opens an `AsyncSession` and stashes it on `request.state.db`) → a fixed-window rate limiter (in-memory dict keyed by client IP, 100 req/60s, defined in `services/rate_limiter.py`). In practice routers don't use `request.state.db` — they instead resolve a session per-endpoint via the `Depends(get_db)` FastAPI dependency (`database/connection.py`), which is the pattern to follow for new endpoints.

### Router prefixes are inconsistent — check before adding frontend calls
Most routers are mounted under `/api/...` (`auth` → `/api/auth`, `projects` → `/api/projects`, `users` → `/api/users`, `data` → `/api/data`, `backtest` → `/api/backtest`), but `strategies` is mounted at `/strategies` with **no** `/api` prefix (`routers/strategies.py`). The frontend mirrors this exactly (`FrontEnd/src/api/strategies.js` calls `/strategies/...` while every other `FrontEnd/src/api/*.js` file calls `/api/...`). Match the existing prefix for whichever router you're touching rather than "fixing" it unilaterally.

### Auth
JWT-based, via `python-jose`. `services/auth_service.py` centralizes token decoding and the `get_current_user` dependency that essentially all protected routes depend on. Passwords are hashed with `bcrypt` directly in `routers/auth.py` (not through the `passlib` `CryptContext` that's imported in `routers/users.py` but unused there). Tokens embed `sub` (email) and `user_id`; the frontend (`FrontEnd/src/state/AuthContext.jsx`) decodes the JWT payload client-side (no verification) just to read `sub`/`user_id` for display, and persists the raw token in `localStorage`.

**Fixed:** `AuthContext.jsx`'s `AuthProvider` used to call `setAuthToken(token)` (which attaches the `Authorization` header to the shared axios `client`) inside a `useEffect`, while several pages (`ProjectsPage.jsx`, `StrategiesPage.jsx`, `DataPage.jsx`, `BacktestResultsPage.jsx`) fire their initial data fetch in their *own* mount-time `useEffect(() => { load() }, [])`. React fires `useEffect` callbacks child-before-parent on mount, and `AuthProvider` wraps the whole app, so on a hard page load/refresh landing directly on one of those routes with a token already in `localStorage`, the page's fetch effect ran and dispatched its request *before* `AuthProvider`'s effect had attached the header — a request with no `Authorization` header 401s (`"Not authenticated"`, from FastAPI's `OAuth2PasswordBearer` in `services/auth_service.py`) even though the user is logged in. It self-resolved on retry/refresh because by then `AuthProvider`'s effect had already run once. `setAuthToken(token)` is now called synchronously in `AuthProvider`'s render body instead of in an effect, so the header is attached before React commits and fires any child effects. If you add another page with a mount-time fetch, this ordering guarantee is why you don't need to special-case it.

### Ownership model
Every mutable resource chains back to a `User` via `owner_id`: `User` → `Project` (`owner_id`) → `Strategy` (`project_id`) → `BacktestResult` (`strategy_id`). There's no direct `owner_id` on `Strategy`/`BacktestResult`, so authorization checks walk the chain — e.g. `strategy.project.owner_id != user.id` (see `services/backtest_service.py`, `routers/strategies.py`, `routers/backtest.py`). Reuse this same walk-the-relationship-chain pattern for any new ownership check rather than adding a denormalized owner field.

### Strategy definition & execution
A `Strategy.parameters` field stores a JSON string like `{"name", "parameters": {...indicator params...}, "rules": {"entry": "...", "exit": "..."}}`. `services/strategy_executor.py`'s `StrategyExecutor` computes all five advertised indicators — SMA, EMA (`ema_period` → `ema`), RSI, Bollinger Bands, MACD (`macd_fast`/`macd_slow`/`macd_signal` → `macd`/`macd_signal_line`/`macd_hist`, built from `_calculate_ema` — reuse that helper rather than adding new `.ewm()` calls) — and evaluates entry/exit condition strings such as `"fast_ma > slow_ma"` **without `eval`** — it whitelists via regex and manually parses `column/number <op> column/number`. This is a deliberate security measure against code injection; any change to condition evaluation must preserve that no arbitrary expression can reach `eval`/`exec`. All five indicators are also selectable in the frontend's Strategy Builder (`FrontEnd/src/components/StrategyBuilder.jsx`) — keep the `INDICATORS` list, `handleSave`'s parameter mapping, and the engine's supported params in sync if you add another.

`_execute_trades` uses capital-based, all-in position sizing (max whole shares affordable, floor division after folding commission into the fill price — see the method for the exact formula) with configurable `commission_pct`/`slippage_pct` (defaults 0.1%/0.05%, passed from `BacktestRequest` down through `backtest_service.run_backtest`). It has no support for shorting, stop-loss/take-profit, or concurrent positions — one position at a time, long-only. `backtest()` returns `{'trades', 'metrics', 'signals', 'equity_curve'}`; `signals` and `equity_curve` are row-record lists (`{'date', ...}` per bar) built via the shared `_format_date` helper, and are persisted on `BacktestResult.signals`/`.equity_curve` (JSON columns).

`_calculate_metrics` computes `total_return`/`return_pct`/`final_capital`/`win_rate`/`num_trades` plus `max_drawdown_pct` and `sharpe_ratio` (bar-over-bar equity returns × √252, assumes daily bars and 0% risk-free rate — not configurable). `final_capital`/`total_return`/`return_pct` prefer the equity curve's last value over the sum of realized exit P&L whenever the curve is non-empty, so an open position at the last bar is still reflected — don't revert this to realized-only math, it was a deliberate fix for a case where the two used to silently disagree.

`services/backtest_service.py` orchestrates a full backtest run: loads `MarketData` rows for a ticker/date range into a pandas `DataFrame`, runs them through `StrategyExecutor`, and persists the resulting `BacktestResult`.

**Fixed:** `strategy.project.owner_id` / `backtest.strategy.project` ownership checks in `services/backtest_service.py`, `routers/backtest.py`, and `routers/strategies.py` (`update_strategy`) used to lazily traverse SQLAlchemy relationships inside async request handlers with no eager-loading configured (`database/models.py` declares no `lazy="selectin"`, `connection.py` uses a plain `async_sessionmaker`), which raised `MissingGreenlet` against a real async session and surfaced as an uncaught 500 rather than the intended 400/403. Every `select(Strategy)`/`select(BacktestResult)` that reaches `.project`/`.strategy` now chains `.options(selectinload(...))` (nested as `selectinload(BacktestResult.strategy).selectinload(Strategy.project)` where both hops are needed). If you add a new ownership check that walks the relationship chain, eager-load it the same way — the regression is covered by `tests/test_backtest_ownership.py` and `tests/test_strategy_ownership.py`, so a plain `select()` without `.options(...)` on this chain will fail the suite.

**Fixed:** `services/backtest_service.py::run_backtest` used to filter `MarketData.date >= start_date`/`<= end_date` using the raw `str` dates straight off `BacktestRequest` (e.g. `"2023-01-01"`). SQLite's `DateTime` bind processor tolerates a bare string and passes it through unchanged, so the SQLite-backed test suite never caught it, but Postgres/asyncpg binds it as `::VARCHAR` and has no `timestamp >= varchar` operator — every real backtest run 500'd (`asyncpg.exceptions.UndefinedFunctionError`) even though tests were green. `start_date`/`end_date` are now parsed to `datetime` via `datetime.fromisoformat(...)` once, up front (raising a 400 on a malformed date instead of a 500 deep in SQLAlchemy), and the parsed values are reused for both the `MarketData` query and the persisted `BacktestResult.start_date`/`.end_date`. If you touch date-range filtering anywhere else in this codebase, parse to `datetime` before it reaches a SQLAlchemy comparison — see the "SQLite tests can hide Postgres-only bugs" note above for how this is regression-tested without needing Postgres in CI.

### Custom-code strategies (sandboxed)
Alongside the rules mode above, `Strategy.parameters` can set `"mode": "custom_code"` (absent key / `"rules"` = today's default, fully backward compatible with every already-persisted strategy), with the Python source living in the previously-unused `Strategy.code` column. A custom-code strategy defines `generate_signals(df) -> pd.Series` (values in `{1, -1, 0}` per bar) instead of `parameters`/`rules` — everything downstream of signal generation (`_execute_trades`, `_calculate_metrics`) is the same shared code path as rules mode; user code's only job is producing the `signal` column.

`services/sandbox_executor.py` + `services/_sandbox_worker.py` run that code in two layers. `check_ast_safety()` statically rejects disallowed imports (only `pandas`/`numpy` permitted), `eval`/`exec`/`open`/etc. calls, and dunder-attribute access before anything is spawned — run both at strategy save time (`routers/strategies.py`'s `create_strategy`/`update_strategy`, via `_validate_custom_code`, for fast feedback) and again defensively inside the child at run time. `run_custom_strategy()` then executes the code in a **separate subprocess** (`_sandbox_worker.py`, invoked via `sys.executable`) with `resource.setrlimit(RLIMIT_AS/RLIMIT_CPU)` set via `preexec_fn` **before** the child's own Python/pandas/numpy import — so the limit must budget for that import's ~250MB virtual-memory baseline, not just the strategy's own data (see `DEFAULT_MEM_LIMIT_MB`) — plus a `subprocess.run(timeout=...)` wall-clock limit and a restricted-`__builtins__` namespace inside the child as defense in depth. OHLCV data crosses into the child via CSV, never pickled (the DataFrame is trusted, but the code is not, so nothing untrusted ever goes through `pickle`); the resulting signal series comes back via a JSON temp file, never over stdout (which is captured during the call so a stray `print()` in user code can't corrupt the channel).

`RLIMIT_CPU` is deliberately set with **soft < hard** (`cpu_limit_s`, `cpu_limit_s + 1`) so the kernel delivers a catchable `SIGXCPU` (mapped to `SandboxTimeoutError`) before falling back to `SIGKILL` a second later — setting soft == hard collapses straight to `SIGKILL`, indistinguishable from an OOM kill, which is what `test_timeout_enforced` caught during development. Don't collapse that gap back to a single value. All of `SandboxValidationError`/`SandboxTimeoutError`/`SandboxMemoryError`/`SandboxRuntimeError`/`SandboxOutputError` are re-raised as a `ValueError` by `StrategyExecutor.backtest()`'s `custom_code` branch, which `backtest_service.py`'s existing `except Exception → HTTPException(400, str(e))` already surfaces cleanly — no new error handling was needed there.

`preexec_fn`-based resource limits are POSIX-only (Linux/macOS) — fine for this repo's Docker-based dev/deploy story, but don't assume this sandbox works unmodified on Windows. Network isolation is **not** provided (no containers/seccomp/namespaces) — mitigated only by the restricted builtins/import allowlist removing any reachable path to `socket`/`os`/`urllib` from user code; accepted as adequate for this project's personal/small-scale use, not multi-tenant SaaS. If this ever needs to hold up under untrusted-at-scale multi-tenant load, move to a container-per-run model instead of trying to patch this one tighter.

Tested in `tests/test_sandbox_executor.py` (AST-check rejections, timeout, memory limit, runtime exceptions, output-shape validation — all via real subprocess execution, no mocks), `tests/test_strategy_executor.py` (the `custom_code` branch through `StrategyExecutor.backtest()`), and `tests/test_strategy_code_validation.py` (save-time validation, including `update_strategy`'s merged-view case where only `code` or only `parameters` is present in a partial-update dict). This feature only touches `Text` columns, not date/type-sensitive SQL, so no Postgres-specific test was needed — but it was hand-verified against a live Postgres backtest via `docker compose up` anyway (create → save-time rejection → real backtest run → runtime-exception 400) per the dialect-sensitivity guidance above.

The frontend's `StrategyBuilder.jsx` exposes this as a "Visual Builder" / "Custom Python Code" toggle; the custom-code panel is a plain `<textarea>` (`.code-editor` in `styles.css`), deliberately not a new CodeMirror/Monaco dependency for this first pass.

`services/data_service.py` has incomplete/broken implementations (e.g. calls `.to_dataframe()` on a plain list of ORM objects, which doesn't exist) — treat it as unfinished scaffolding, not a working reference.

### Market data import (`routers/data.py`)
All endpoints below are under `/api/data`, require auth, and have no ownership (any authenticated user can read/write any ticker's data — see Data models below). Three ways to write bars in, three to read them back, one to delete:
- `POST /upload` — single bar, JSON body (`MarketDataCreate`: `ticker`, `date`, OHLCV, optional `adj_close`).
- `POST /upload-csv` — bulk, multipart (`ticker` form field + `file`). Expects `Date,Open,High,Low,Close,Volume[,Adj Close]`-style columns (case/space-insensitive).
- `POST /import/{ticker}` — bulk, fetches daily history from **Alpha Vantage** (`TIME_SERIES_DAILY`, `outputsize=full`) and imports it. Needs a real API key for any symbol beyond the demo one — see Environment above. This used to hit Stooq's free CSV export instead; Stooq now gates that endpoint behind a client-side JS proof-of-work challenge specifically to block scripted requests (confirmed by hand: a plain request gets an immediate 404, a browser-UA'd one gets the unsolvable challenge page instead of data), so it no longer works from a server-side client. Don't reintroduce Stooq scraping here without solving that — which would mean building bot-detection evasion — instead of just picking a documented API.
- `GET /tickers` — distinct tickers, alphabetical.
- `GET /{ticker}/range` — `{ticker, start_date, end_date, count}`, the min/max date and row count on file for a ticker; 404s if none. Used by the frontend to constrain a backtest's date pickers to a range that actually has data (see Frontend structure below).
- `GET /{ticker}/historical` — optional `start_date`/`end_date` query params, always ordered by date — mirrors the exact query `backtest_service.run_backtest` issues, so this doubles as a "preview what a backtest would load" endpoint.
- `DELETE /{data_id}` — single row.

`upload-csv` and `import/{ticker}` both funnel through the module-private `_bulk_upsert_market_data(ticker, df, db)` helper, which normalizes column names, requires `date/open/high/low/close/volume`, and skips any `(ticker, date)` pair already stored rather than erroring on the unique constraint — keep new bulk-import paths going through this helper rather than reimplementing insert/skip logic.

### Frontend structure
- `src/api/*.js` — one module per backend resource, thin axios wrappers around the shared `client.js` (base URL from `VITE_API_BASE`, JWT injected via `setAuthToken`). `src/api/data.js` covers the `routers/data.py` endpoints above.
- `src/state/AuthContext.jsx` — the only global state; holds the JWT and exposes `login`/`register`/`logout`.
- `src/components/ProtectedRoute.jsx` — gates routes on `useAuth().isAuthenticated`; used in `App.jsx` for `/projects`, `/data`, `/projects/:projectId/strategies`, `/strategies/:strategyId/backtest`.
- Page components under `src/pages/` correspond 1:1 with those routes. `DataPage.jsx` (`/data`) is the market-data-import UI (CSV upload + Alpha Vantage import, the latter's API key entered in the UI and persisted client-side in `localStorage` under `quanttrade_alpha_vantage_api_key` — not sent anywhere but this app's own backend). `StrategiesPage.jsx`'s backtest form sources its ticker `<select>` from `GET /api/data/tickers` and constrains the start/end date `<input type="date">` `min`/`max` from `GET /api/data/{ticker}/range`, so the UI can't submit a range with no underlying data.

**Fixed:** `src/styles.css`'s global `input, textarea, select` rule sets `color: var(--fg)` (light text) for the closed `<select>` control, which reads fine against its own near-transparent dark background. But `background` set on a `<select>` doesn't carry into the browser's native opened-option-list popup (Chrome/Edge fall back to a default white popup background), while `<option>` still inherits the light `--fg` text color — so every dropdown's open state rendered white-on-white. Fixed with an explicit `select option { background: #10141f; color: var(--fg); }` rule. If you add another themed form control whose popup/native rendering is separate from its closed state (e.g. `<datalist>`), check the opened state specifically rather than just the closed control.

### Data models (`BackEnd/database/models.py`)
`User` 1—N `Project` 1—N `Strategy` 1—N `BacktestResult`. `MarketData` is independent (keyed by `ticker`+`date`, unique-constrained), not owned by a user — it's shared reference data that any authenticated user can query/upload/delete via `routers/data.py`. `BacktestResult` stores `results` (metrics), `trades`, `signals`, and `equity_curve` as JSON columns. There's no migration tooling (`init_db()` only runs `Base.metadata.create_all`, which won't alter an existing table) — if you add/change columns, the local dev DB's tables need to be dropped and recreated manually.
