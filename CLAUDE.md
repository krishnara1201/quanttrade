# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

QuantTrade is a full-stack trading strategy backtesting platform: a FastAPI backend (`BackEnd/`) and a React + Vite frontend (`FrontEnd/`). Users create projects, define trading strategies (via indicators + entry/exit rules, or sandboxed custom Python signal code — see Strategy definition & execution below), and run backtests against stored market data.

## Commands

### Backend (`BackEnd/`)
Dependencies are managed with [uv](https://docs.astral.sh/uv/) via `BackEnd/pyproject.toml`/`uv.lock` — there is no `requirements.txt` and no manually-created venv; `uv` creates and manages `BackEnd/.venv` itself from the lockfile.
```bash
cd BackEnd
uv sync          # creates .venv and installs pinned deps + dev group (pytest et al.)
uv run uvicorn app:app --reload
```
`uv add <package>`/`uv remove <package>` (run from `BackEnd/`) update both `pyproject.toml` and `uv.lock` together — edit dependency versions through these rather than hand-editing `pyproject.toml`, so the lockfile never drifts out of sync. Runtime deps live under `[project.dependencies]`; test-only deps (`pytest`, `pytest-asyncio`, `aiosqlite`) live in the `dev` group under `[dependency-groups]` — add new deps to whichever one matches, e.g. `uv add --dev <package>` for a test-only dep.

Alternatively, run the full stack (Postgres included) via `docker compose up` from the repo root — see `README.md`'s Docker Setup section. `BackEnd/Dockerfile` also uses `uv` (via the official `ghcr.io/astral-sh/uv` image, copied in as a static binary) and runs `uv sync --locked` at build time, so a dependency change needs `docker compose up --build` to take effect, same as before.

### Tests
```bash
cd BackEnd
uv run pytest tests/ -v
```
Must be run from `BackEnd/` (or with `BackEnd` on `PYTHONPATH`) — `tests/__init__.py` relies on pytest's rootdir-relative import mode to resolve `from services...` imports; running `pytest BackEnd/tests` from the repo root will fail to import. There is no `pytest.ini`/`conftest.py` pinning this.

Test coverage: `services/strategy_executor.py` (`tests/test_strategy_executor.py`) — indicator correctness, position sizing/costs, and metrics, all unit-tested with hand-verified expected values (no mocks, no DB). `tests/test_backtest_ownership.py` and `tests/test_strategy_ownership.py` cover the ownership-check async regression (see below) against a real async session, using an in-memory `sqlite+aiosqlite` engine (dev-only deps `pytest-asyncio`/`aiosqlite`, pinned in the `dev` group of `pyproject.toml`) rather than mocks — `pytest.ini` sets `asyncio_default_fixture_loop_scope = function`. `tests/test_data_upload.py`, `tests/test_data_historical.py`, and `tests/test_data_import.py` cover `routers/data.py` the same way. There is otherwise no test suite for routers/services that touch the database, and no frontend test suite.

**SQLite tests can hide Postgres-only bugs — verify dialect-sensitive fixes against real Postgres too.** `test_backtest_ownership.py::test_run_backtest_queries_market_data_with_datetime_not_raw_string` exists because SQLite's `DateTime` bind processor passes a raw Python `str` through unchanged (so `MarketData.date >= "2024-01-01"` "works" against SQLite), while Postgres/asyncpg binds it as `::VARCHAR` and rejects `timestamp >= varchar` outright — a bug the SQLite-only suite could never catch by actually hitting Postgres. That test instead asserts on the *type* of the value SQLAlchemy binds into the compiled query (via `stmt.compile(compile_kwargs={"literal_binds": False}).params`), which is dialect-independent and catches the same class of bug. When a fix depends on Postgres-specific type strictness (as opposed to ORM-relationship behavior, which SQLite reproduces fine per the ownership-check regression below), don't trust a SQLite-only green suite — run `docker compose up` and exercise the real endpoint against the `postgres` service before calling it fixed.

### Environment
Copy `BackEnd/.env.example` to `BackEnd/.env` and set `SECRET_KEY` (JWT signing) and `ALGORITHM` (e.g. `HS256`); both are read via `os.getenv` in `services/auth_service.py` with no defaults, so the app will error on auth routes if unset. `CORS_ORIGINS` is a comma-separated list consumed in `app.py`. `DATABASE_URL` is read from the environment in `database/connection.py` (via `os.getenv`, falling back to `postgresql+asyncpg://postgres:postgres@localhost/quanttrade` if unset) — set it in `.env` to point at a different Postgres instance. The Docker Compose stack (`docker-compose.yml`) overrides it to point at the `postgres` service. `ALPHA_VANTAGE_API_KEY` is optional — read via `os.getenv` in `routers/data.py`, falls back to Alpha Vantage's public `"demo"` key (which only serves a handful of sample symbols, e.g. `IBM`) if unset; can also be overridden per-request via the `api_key` query param on `POST /api/data/import/{ticker}`.

## Architecture

### Backend request flow
`app.py` wires global middleware (in registration order, so the *last*-added middleware runs *first* per Starlette's stack): CORS → per-request DB session middleware (opens an `AsyncSession` and stashes it on `request.state.db`) → a fixed-window rate limiter (in-memory dict keyed by client IP, 100 req/60s, defined in `services/rate_limiter.py`). In practice routers don't use `request.state.db` — they instead resolve a session per-endpoint via the `Depends(get_db)` FastAPI dependency (`database/connection.py`), which is the pattern to follow for new endpoints.

### Router prefixes are inconsistent — check before adding frontend calls
Most routers are mounted under `/api/...` (`auth` → `/api/auth`, `projects` → `/api/projects`, `users` → `/api/users`, `data` → `/api/data`, `backtest` → `/api/backtest`), but `strategies` is mounted at `/strategies` with **no** `/api` prefix (`routers/strategies.py`). The frontend mirrors this exactly (`FrontEnd/src/api/strategies.js` calls `/strategies/...` while every other `FrontEnd/src/api/*.js` file calls `/api/...`). Match the existing prefix for whichever router you're touching rather than "fixing" it unilaterally.

### Auth
JWT-based, via `python-jose`. `services/auth_service.py` centralizes token decoding and the `get_current_user` dependency that essentially all protected routes depend on. Passwords are hashed with `bcrypt` directly in `routers/auth.py` (not through the `passlib` `CryptContext` that's imported in `routers/users.py` but unused there). Tokens embed `sub` (email) and `user_id`; the frontend (`FrontEnd/src/state/AuthContext.jsx`) decodes the JWT payload client-side (no verification) just to read `sub`/`user_id` for display, and persists the raw token in `localStorage`.

**Fixed:** `AuthContext.jsx`'s `AuthProvider` used to call `setAuthToken(token)` (which attaches the `Authorization` header to the shared axios `client`) inside a `useEffect`, while several pages (`ProjectsPage.jsx`, `StrategiesPage.jsx`, `DataPage.jsx`, `BacktestResultsPage.jsx`) fire their initial data fetch in their *own* mount-time `useEffect(() => { load() }, [])`. React fires `useEffect` callbacks child-before-parent on mount, and `AuthProvider` wraps the whole app, so on a hard page load/refresh landing directly on one of those routes with a token already in `localStorage`, the page's fetch effect ran and dispatched its request *before* `AuthProvider`'s effect had attached the header — a request with no `Authorization` header 401s (`"Not authenticated"`, from FastAPI's `OAuth2PasswordBearer` in `services/auth_service.py`) even though the user is logged in. It self-resolved on retry/refresh because by then `AuthProvider`'s effect had already run once. `setAuthToken(token)` is now called synchronously in `AuthProvider`'s render body instead of in an effect, so the header is attached before React commits and fires any child effects. If you add another page with a mount-time fetch, this ordering guarantee is why you don't need to special-case it.

### Ownership model
Every mutable resource chains back to a `User` via `owner_id`: `User` → `Project` (`owner_id`) → `Strategy` (`project_id`) → `BacktestResult` (`strategy_id`). There's no direct `owner_id` on `Strategy`/`BacktestResult`, so authorization checks walk the chain — e.g. `strategy.project.owner_id != user.id` (see `services/backtest_service.py`, `routers/strategies.py`, `routers/backtest.py`). Reuse this same walk-the-relationship-chain pattern for any new ownership check rather than adding a denormalized owner field.

### Strategy definition & execution
A `Strategy.parameters` field stores a JSON string like `{"name", "parameters": {...indicator params...}, "rules": {"entry": "...", "exit": "..."}}`. `services/strategy_executor.py`'s `StrategyExecutor` computes all five advertised indicators — SMA, EMA (`ema_period` → `ema`), RSI, Bollinger Bands, MACD (`macd_fast`/`macd_slow`/`macd_signal` → `macd`/`macd_signal_line`/`macd_hist`, built from `_calculate_ema` — reuse that helper rather than adding new `.ewm()` calls) — and evaluates entry/exit condition strings such as `"fast_ma > slow_ma"` **without `eval`** — it whitelists via regex and manually parses `column/number <op> column/number`. This is a deliberate security measure against code injection; any change to condition evaluation must preserve that no arbitrary expression can reach `eval`/`exec`. All five indicators are also selectable in the frontend's Strategy Builder (`FrontEnd/src/components/StrategyBuilder.jsx`) — keep the `INDICATORS` list, `handleSave`'s parameter mapping, and the engine's supported params in sync if you add another.

`_execute_trades` uses capital-based, all-in position sizing (max whole shares affordable, floor division after folding commission into the fill price — see the method for the exact formula) with configurable `commission_pct`/`slippage_pct` (defaults 0.1%/0.05%, passed from `BacktestRequest` down through `backtest_service.run_backtest`). `_execute_trades` also takes optional `allow_short` (bool, per-run — not saved on the strategy) and `stop_loss_pct`/`take_profit_pct` (per-run, both `None` by default). With `allow_short=True`, `signal=-1` while flat opens a short (mirroring `signal=1` while flat opening a long) rather than being ignored; `signal=1` while short closes the short and, since the account is then flat, can open a new long the same bar, and symmetrically `signal=-1` while long closes the long and can open a new short the same bar — both reflips reuse the same `_open_position`/`_close_position` call for the exit and a second one for the re-entry within a single bar's iteration. `stop_loss_pct`/`take_profit_pct`, when set, force a close-only exit each bar, checked against that bar's close price before that bar's own signal is evaluated — so a forced exit can still be followed by a same-bar re-entry from the signal. There's still no concurrent/multi-position support — one position at a time, long or short. Entry trades now carry a `direction` field (`"long"`/`"short"`) and exit trades carry `exit_reason` (`"signal"`/`"stop_loss"`/`"take_profit"`), both additive fields alongside the existing trade shape. `backtest()` returns `{'trades', 'metrics', 'signals', 'equity_curve'}`; `signals` and `equity_curve` are row-record lists (`{'date', ...}` per bar) built via the shared `_format_date` helper, and are persisted on `BacktestResult.signals`/`.equity_curve` (JSON columns).

`_calculate_metrics` computes `total_return`/`return_pct`/`final_capital`/`win_rate`/`num_trades` plus `max_drawdown_pct` and `sharpe_ratio` (bar-over-bar equity returns × √252, assumes daily bars and 0% risk-free rate — not configurable). `final_capital`/`total_return`/`return_pct` prefer the equity curve's last value over the sum of realized exit P&L whenever the curve is non-empty, so an open position at the last bar is still reflected — don't revert this to realized-only math, it was a deliberate fix for a case where the two used to silently disagree.

`services/backtest_service.py` orchestrates a full backtest run: loads `MarketData` rows for a ticker/date range into a pandas `DataFrame`, runs them through `StrategyExecutor`, and persists the resulting `BacktestResult`.

**Fixed:** `strategy.project.owner_id` / `backtest.strategy.project` ownership checks in `services/backtest_service.py`, `routers/backtest.py`, and `routers/strategies.py` (`update_strategy`) used to lazily traverse SQLAlchemy relationships inside async request handlers with no eager-loading configured (`database/models.py` declares no `lazy="selectin"`, `connection.py` uses a plain `async_sessionmaker`), which raised `MissingGreenlet` against a real async session and surfaced as an uncaught 500 rather than the intended 400/403. Every `select(Strategy)`/`select(BacktestResult)` that reaches `.project`/`.strategy` now chains `.options(selectinload(...))` (nested as `selectinload(BacktestResult.strategy).selectinload(Strategy.project)` where both hops are needed). If you add a new ownership check that walks the relationship chain, eager-load it the same way — the regression is covered by `tests/test_backtest_ownership.py` and `tests/test_strategy_ownership.py`, so a plain `select()` without `.options(...)` on this chain will fail the suite.

**Fixed:** `services/backtest_service.py::run_backtest` used to filter `MarketData.date >= start_date`/`<= end_date` using the raw `str` dates straight off `BacktestRequest` (e.g. `"2023-01-01"`). SQLite's `DateTime` bind processor tolerates a bare string and passes it through unchanged, so the SQLite-backed test suite never caught it, but Postgres/asyncpg binds it as `::VARCHAR` and has no `timestamp >= varchar` operator — every real backtest run 500'd (`asyncpg.exceptions.UndefinedFunctionError`) even though tests were green. `start_date`/`end_date` are now parsed to `datetime` via `datetime.fromisoformat(...)` once, up front (raising a 400 on a malformed date instead of a 500 deep in SQLAlchemy), and the parsed values are reused for both the `MarketData` query and the persisted `BacktestResult.start_date`/`.end_date`. If you touch date-range filtering anywhere else in this codebase, parse to `datetime` before it reaches a SQLAlchemy comparison — see the "SQLite tests can hide Postgres-only bugs" note above for how this is regression-tested without needing Postgres in CI.

### Custom-code strategies (sandboxed)
Alongside the rules mode above, `Strategy.parameters` can set `"mode": "custom_code"` (absent key / `"rules"` = today's default, fully backward compatible with every already-persisted strategy), with the Python source living in the previously-unused `Strategy.code` column. A custom-code strategy defines `generate_signals(df) -> pd.Series` (values in `{1, -1, 0}` per bar) instead of `parameters`/`rules` — everything downstream of signal generation (`_execute_trades`, `_calculate_metrics`) is the same shared code path as rules mode; user code's only job is producing the `signal` column.

`services/sandbox_executor.py` + `services/_sandbox_worker.py` run that code in two layers. `check_ast_safety()` statically rejects disallowed imports (`pandas`/`numpy`, plus a curated set of `sklearn` submodules — see below), `eval`/`exec`/`open`/etc. calls, and dunder-attribute access before anything is spawned — run both at strategy save time (`routers/strategies.py`'s `create_strategy`/`update_strategy`, via `_validate_custom_code`, for fast feedback) and again defensively inside the child at run time. `run_custom_strategy()` then executes the code in a **separate subprocess** (`_sandbox_worker.py`, invoked via `sys.executable`) with `resource.setrlimit(RLIMIT_AS/RLIMIT_CPU)` set via `preexec_fn` **before** the child's own Python/pandas/numpy import — so the limit must budget for that import's ~250MB virtual-memory baseline, not just the strategy's own data (see `DEFAULT_MEM_LIMIT_MB`) — plus a `subprocess.run(timeout=...)` wall-clock limit and a restricted-`__builtins__` namespace inside the child as defense in depth. OHLCV data crosses into the child via CSV, never pickled (the DataFrame is trusted, but the code is not, so nothing untrusted ever goes through `pickle`); the resulting signal series comes back via a JSON temp file, never over stdout (which is captured during the call so a stray `print()` in user code can't corrupt the channel).

`RLIMIT_CPU` is deliberately set with **soft < hard** (`cpu_limit_s`, `cpu_limit_s + 1`) so the kernel delivers a catchable `SIGXCPU` (mapped to `SandboxTimeoutError`) before falling back to `SIGKILL` a second later — setting soft == hard collapses straight to `SIGKILL`, indistinguishable from an OOM kill, which is what `test_timeout_enforced` caught during development. Don't collapse that gap back to a single value. All of `SandboxValidationError`/`SandboxTimeoutError`/`SandboxMemoryError`/`SandboxRuntimeError`/`SandboxOutputError` are re-raised as a `ValueError` by `StrategyExecutor.backtest()`'s `custom_code` branch, which `backtest_service.py`'s existing `except Exception → HTTPException(400, str(e))` already surfaces cleanly — no new error handling was needed there.

**ML strategies via scikit-learn.** `ALLOWED_IMPORT_PREFIXES` in `sandbox_executor.py` also permits a curated set of `sklearn` submodules (`linear_model`, `ensemble`, `tree`, `svm`, `naive_bayes`, `neighbors`, `preprocessing`, `pipeline`, `model_selection`, `metrics`) so `generate_signals(df)` can train and predict with a model inline — deliberately not `sklearn.datasets` (network fetchers) or any other unreviewed submodule. Matching is by full dotted path, not just the root package (`_import_is_allowed()`), shared identically between `check_ast_safety`'s static check and `_sandbox_worker.py`'s `_safe_import` runtime check (kept as a literal duplicate list there, not an import, since the worker runs as a standalone script) — so `from sklearn.linear_model import LogisticRegression` is allowed but bare `import sklearn` and the `from sklearn import linear_model` shorthand are both rejected (the latter's module name is just `"sklearn"`, which matches no curated prefix). If you add another submodule to the allowlist, update both lists together or the worker's runtime check silently diverges from what save-time validation already accepted. Because sklearn estimators can spawn worker subprocesses via `joblib`/`loky` when `n_jobs != 1` — each with its own fresh `RLIMIT_AS`/`RLIMIT_CPU` budget entirely outside the parent's intended cap — `run_custom_strategy()` passes `SINGLE_THREAD_ENV` (`OMP_NUM_THREADS`/`OPENBLAS_NUM_THREADS`/`MKL_NUM_THREADS=1`, `JOBLIB_MULTIPROCESSING=0`, `LOKY_MAX_CPU_COUNT=1`) as the subprocess's `env`, so training stays inside the one resource-limited process regardless of what `n_jobs` the user's code requests. Walk-forward evaluation (see "Walk-forward backtests" below) is the opt-in way to avoid this look-ahead bias — it re-runs `generate_signals(df)` fresh per expanding fold instead of once over the whole range. It's opt-in, not enforced: a strategy run through the ordinary single-ticker/portfolio paths above still fits a model on the whole `df` before predicting, training on future data, and that remains on the strategy author to avoid by choosing walk-forward mode. Even within walk-forward mode the leakage boundary is deliberately non-strict — see "Walk-forward backtests" below.

`DEFAULT_TIMEOUT_S`/`DEFAULT_MEM_LIMIT_MB`/`DEFAULT_CPU_LIMIT_S` read from `SANDBOX_TIMEOUT_S`/`SANDBOX_MEM_LIMIT_MB`/`SANDBOX_CPU_LIMIT_S` env vars (via `os.getenv`, same `load_dotenv()`-then-`os.getenv` pattern as `database/connection.py`), falling back to the original hardcoded values (10s / 512MB / 8s) when unset — so tuning them for e.g. heavier sklearn training is a `.env` edit, not a code change. Left at the fallback values by default since dev currently runs on a resource-constrained host; raise them (`BackEnd/.env.example` documents the three vars) if sklearn training starts hitting the ceiling.

`preexec_fn`-based resource limits are POSIX-only (Linux/macOS) — fine for this repo's Docker-based dev/deploy story, but don't assume this sandbox works unmodified on Windows. Network isolation is **not** provided (no containers/seccomp/namespaces) — mitigated only by the restricted builtins/import allowlist removing any reachable path to `socket`/`os`/`urllib` from user code; accepted as adequate for this project's personal/small-scale use, not multi-tenant SaaS. If this ever needs to hold up under untrusted-at-scale multi-tenant load, move to a container-per-run model instead of trying to patch this one tighter.

Tested in `tests/test_sandbox_executor.py` (AST-check rejections, timeout, memory limit, runtime exceptions, output-shape validation, the curated-sklearn-submodule allow/reject cases, an end-to-end `LogisticRegression` fit+predict through `run_custom_strategy`, the forced-single-thread env vars passed to the subprocess, and the env-configurable resource-limit defaults — the last verified via a real subprocess import rather than `importlib.reload`, since reloading `sandbox_executor` in-process would desync its exception classes from the copies `routers/strategies.py` already imported by reference, breaking `except SandboxValidationError` elsewhere in the suite; all via real subprocess execution, no mocks), `tests/test_strategy_executor.py` (the `custom_code` branch through `StrategyExecutor.backtest()`), and `tests/test_strategy_code_validation.py` (save-time validation, including `update_strategy`'s merged-view case where only `code` or only `parameters` is present in a partial-update dict). This feature only touches `Text` columns, not date/type-sensitive SQL, so no Postgres-specific test was needed — but it was hand-verified against a live Postgres backtest via `docker compose up` anyway (create → save-time rejection → real backtest run → runtime-exception 400) per the dialect-sensitivity guidance above.

The frontend's `StrategyBuilder.jsx` exposes this as a "Visual Builder" / "Custom Python Code" toggle; the custom-code panel is a plain `<textarea>` (`.code-editor` in `styles.css`), deliberately not a new CodeMirror/Monaco dependency for this first pass.

`services/data_service.py` has incomplete/broken implementations (e.g. calls `.to_dataframe()` on a plain list of ORM objects, which doesn't exist) — treat it as unfinished scaffolding, not a working reference.

### Portfolio-level backtests
`services/portfolio_backtest_service.py` adds a second backtest mode, run independently of `services/backtest_service.py`: given a strategy and a basket of ≥2 tickers with custom weights (`normalize_weights` auto-normalizes weights to sum to 1.0 — they don't need to already sum to 100), it splits `initial_capital` into a fixed per-ticker sub-account (`initial_capital * normalized_weight`) and runs each ticker independently through the same unmodified `StrategyExecutor.backtest()` used by the single-ticker path — no rebalancing, no cross-ticker conditions, one strategy applied identically to every ticker in the basket. `_check_ticker_coverage` rejects the whole request with a 400 naming the offending ticker if any ticker's data doesn't span the full `[start_date, end_date]` range (mirrors `GET /api/data/{ticker}/range`'s min/max/count check). `aggregate_equity_curves` combines per-ticker equity curves into one portfolio curve via a date-union with forward-fill (a ticker missing a bar on a given date carries forward its last-known equity, or its starting `allocated_capital` before its first bar) — no capital ever moves between tickers. `aggregate_portfolio_metrics` pools trades across all tickers into one set of metrics using the exact same field names as a single-ticker backtest's metrics (`total_return`, `return_pct`, `final_capital`, `win_rate`, `num_trades`, `max_drawdown_pct`, `sharpe_ratio` — the latter two via `max_drawdown_pct`/`sharpe_ratio`, pulled out of `StrategyExecutor` as module-level functions in `strategy_executor.py` so both paths share the same math) so the frontend can render either result type with the same components.

Results persist to a separate `PortfolioBacktestResult` table (`database/models.py`), not `BacktestResult` — this is an additive new mode; the single-ticker table/endpoints/tests are unmodified. New endpoints on the existing `/api/backtest`-prefixed router (`routers/backtest.py`): `POST /run-portfolio`, `GET /portfolio/results/{strategy_id}`, `GET /portfolio/{portfolio_backtest_id}`. The service layer raises `ValueError` for every validation/ownership/execution failure; the router translates it to an HTTP status via a 3-way mapping (`"Unauthorized"` → 403, `"not found"` in the message → 404, else → 400) — a new service function that reaches `.project`/`.strategy` must eager-load with `selectinload` the same way `run_backtest`/`get_backtest_detail` already do, or it'll hit the same `MissingGreenlet` regression documented above.

**Fixed:** `run_portfolio_backtest` originally only validated a ticker's *global* min/max date range against the request (`_check_ticker_coverage`), which deliberately tolerates interior gaps (the aggregate equity curve forward-fills those). But a ticker whose global range technically covers the request while having zero bars in that specific sub-window (e.g. bars far outside a narrow requested window, common with chunked CSV/API imports) hit an unhandled `KeyError` — `pd.DataFrame([])` from a zero-row query has no `date` column, and `df.set_index("date", inplace=True)` isn't inside the function's `try/except`. Fixed with an explicit `if not rows: raise ValueError(...)` right after the per-ticker `MarketData` query, before the DataFrame is built — matching `backtest_service.run_backtest`'s existing empty-rows guard. If you touch the per-ticker data-loading loop in `portfolio_backtest_service.py`, keep this guard; it's covered by `tests/test_portfolio_backtest_service.py`.

Frontend: `StrategiesPage.jsx`'s backtest form gets a "Single ticker / Portfolio" toggle — portfolio mode replaces the ticker `<select>` with repeatable ticker+weight rows (add/remove, weights don't need to sum to 100). `BacktestResultsPage.jsx` merges single-ticker and portfolio results into one list (portfolio rows badged "Portfolio · N tickers"), and a portfolio result's detail view shows the aggregate metrics (same `metrics-grid` markup as single-ticker, since field names match) plus an expandable per-ticker breakdown, each reusing the existing `BacktestChart.jsx` unmodified — `BacktestChart` got one addition, an optional `priceName` prop (default `'Stock Price'`) so the portfolio aggregate chart's top panel can be labeled `"Portfolio Equity"` instead, with `equityCurve={[]}` passed to suppress the (otherwise duplicate) bottom equity panel.

Tested in `tests/test_portfolio_backtest_service.py` (weight normalization, coverage validation, equity-curve aggregation incl. forward-fill, pooled metrics, the full orchestrator, ownership-check regressions, router error-translation — no mocks, real in-memory `sqlite+aiosqlite`), and hand-verified against a live Postgres run via `docker compose up` (table creation, a real portfolio backtest end-to-end).

### Walk-forward backtests
`services/walk_forward_service.py` adds a third backtest mode, scoped to `custom_code` strategies only — a rules-mode strategy is rejected with a 400 (`"Walk-forward evaluation requires a custom-code strategy"`) since rules-based strategies don't fit anything, so there's no look-ahead leakage to guard against. Instead of `StrategyExecutor.backtest()` generating signals once over the whole requested range (today's behavior for single-ticker/portfolio runs — see the "look-ahead bias" note in Custom-code strategies above), walk-forward splits `[start_date, end_date]` into expanding train/test folds and re-runs signal generation fresh per fold, stitching the out-of-sample (OOS) results into one continuous equity curve with capital compounding across folds.

`compute_fold_boundaries(start_dt, end_dt, test_window_days)` computes the fold schedule: the first fold's train window is `max(365 days, 25% of the total range)` anchored at `start_dt`, then each fold's `test_window_days`-long test window steps forward from the end of the previous fold's test window, with the train window always expanding from `start_dt` through the start of that fold's test window. A trailing remainder shorter than `test_window_days` is dropped rather than becoming a short partial fold; a range that doesn't fit even one full fold raises `ValueError("date range too short for the requested test window")`. `estimate_fold_count(start_dt, end_dt, test_window_days)` is a deliberately conservative (at-or-above-actual) fold-count estimate — it skips the initial-train-window subtraction `compute_fold_boundaries` applies — used to size the Celery task's `time_limit`/`soft_time_limit` at enqueue time, before the market data needed to compute real fold boundaries has even been loaded.

Per fold, `execute_walk_forward` slices `df` from `start_date` through that fold's `test_end` (train+test rows), calls `StrategyExecutor.generate_signals()` (extracted out of `backtest()` specifically to support this — see `strategy_executor.py`) on that slice, truncates down to just `[test_start, test_end]`, and runs the truncated slice through the same shared `_execute_trades()` every other mode uses, with `initial_capital` set to the *previous* fold's ending equity (`running_capital`) — so capital compounds across folds into one continuous OOS curve rather than N independent mini-backtests. Each fold's trades/equity rows are appended to the run's pooled `trades`/`equity_curve` in chronological order, with every `equity_curve` row tagged `fold_index` so the frontend can shade fold boundaries; `folds` holds one summary dict per fold (`fold_index`, `train_start`/`train_end`/`test_start`/`test_end`, `return_pct`, `num_trades`) for the per-fold breakdown table. `folds_completed` is bumped and committed after each fold finishes (a partial-progress commit distinct from the final result write) so `GET /walk-forward/{id}` can be polled for `{status: "running", folds_completed, total_folds}` instead of showing an opaque spinner for what can be a multi-minute run of N sequential sandboxed subprocess calls. Any single fold's failure (a `SandboxTimeoutError`/`SandboxMemoryError`/`SandboxRuntimeError`/`SandboxOutputError`/`ValueError` out of that fold's `generate_signals`/`_execute_trades` call) fails the **entire** run — no partial-success state, since a stitched curve with a gap in it isn't meaningful — with `error_message` naming which fold failed (e.g. `"Fold 4/8 failed: SandboxTimeoutError: ..."`).

**Fold boundaries settle any open position for free, with no exit trade recorded.** Each fold's `_execute_trades(test_slice, fold_start_capital, ...)` call always starts flat with `cash = fold_start_capital` — if the previous fold ended holding an open position, that position's mark-to-market value silently becomes the next fold's starting cash, with no commission, no slippage, and no `exit` trade appended to `all_trades`. This means `num_trades`/`win_rate` (computed from exit trades only) undercount, and returns are biased slightly upward at every fold boundary for an always-in-market strategy. This is deliberate, spec'd behavior (each fold runs `_execute_trades` independently), not a bug — but it means `num_trades`/`win_rate`/returns from a walk-forward run are **not directly comparable** to an equivalent single continuous backtest of the same strategy over the same period, especially for always-in-market strategies with short test windows. A real fix (e.g. carrying the open position itself across the boundary rather than just its mark-to-market value) would change historical result numbers and needs its own design discussion — see `execute_walk_forward`'s docstring in `services/walk_forward_service.py` and the note surfaced near the per-fold breakdown table in `BacktestResultsPage.jsx`.

Aggregate `results` are computed via the same module-level `_calculate_metrics` call every other mode uses, over the full pooled `trades`/`equity_curve` (same field names as `BacktestResult.results` — `total_return`, `return_pct`, `final_capital`, `win_rate`, `num_trades`, `max_drawdown_pct`, `sharpe_ratio`), so the frontend's existing `metrics-grid` markup renders it with no changes. The benchmark overlay (see below) is computed over the same stitched OOS date range (`folds[0].test_start` through `folds[-1].test_end`), not the full requested range, since that's the span the OOS equity curve actually covers.

**Leakage boundary is intentionally non-strict.** Each fold's `generate_signals(df)` call sees that fold's *entire* train+test slice, not just the train rows — this prevents a fold from seeing data from *future* folds, but does not prevent a model from fitting on rows that fall inside its own fold's test window. A stricter `generate_signals(df, train_end_idx)` contract was considered and explicitly deferred (see the spec's Future Work) as a larger lift than this feature's scope — every existing custom-code strategy would need to become walk-forward-aware to benefit from it.

Results persist to a separate `WalkForwardBacktestResult` table (`database/models.py`), not `BacktestResult` — additive new mode, single-ticker/portfolio tables/endpoints/tests are unmodified. New endpoints on the existing `/api/backtest`-prefixed router (`routers/backtest.py`): `POST /run-walk-forward`, `GET /walk-forward/results/{strategy_id}`, `GET /walk-forward/{walk_forward_backtest_id}`. `create_pending_walk_forward_backtest`/`get_walk_forward_backtest_results`/`get_walk_forward_backtest_detail` follow the exact same `ValueError`-raises → router 3-way-maps-to-403/404/400 pattern as the portfolio service, with the same `selectinload(...)` eager-loading requirement on any new function that walks `.strategy`/`.project`. `create_pending_walk_forward_backtest` also validates `test_window_days >= 30` (rejecting anything smaller with a `ValueError`) — a single-digit `test_window_days` over a multi-year date range would otherwise produce thousands of sequential sandboxed subprocess launches and a Celery time limit measured in hours from one API request; the UI only ever offers 3/6/12-month options, but this guards the API directly rather than relying on the frontend not sending something smaller.

`walk_forward_task` (`tasks.py`) is a thin sync wrapper around `execute_walk_forward` via `asyncio.run(...)`, matching the other four tasks' shape exactly — but unlike those four, which use `.delay(...)`, the router calls `walk_forward_task.apply_async(args=[record.id], time_limit=..., soft_time_limit=...)` with a per-call time limit sized from `estimate_fold_count` at enqueue time (since a walk-forward run's total duration scales with fold count in a way the other four tasks' work doesn't), wrapped in the same try/except-then-503-on-enqueue-failure pattern as the other four `.delay(...)` call sites.

Tested in `tests/test_walk_forward_service.py` (fold-boundary math incl. short-range rejection and remainder-dropping, capital compounding pinned against hand-verified expected values, stitched `trades`/`equity_curve` correctness and `fold_index` tagging, rules-mode rejection, the `test_window_days >= 30` floor, empty-`MarketData`/range-too-short guards, `folds_completed`/`total_folds` progress updates, ownership-check regressions, a fold-failure test that names the failing fold, and one true end-to-end run of the literal LogisticRegression example shown in `StrategiesPage.jsx`'s walk-forward panel across multiple real sandboxed folds — no mocks, real in-memory `sqlite+aiosqlite`, real sandbox subprocess execution throughout).

### Buy-and-hold benchmark overlay
`benchmark_equity_curve(df, initial_capital)`, a module-level function in `strategy_executor.py` (alongside `max_drawdown_pct`/`sharpe_ratio`), computes a reference buy-and-hold curve from OHLCV data already loaded for a backtest: `shares = initial_capital / first_bar.close`, then `equity[t] = shares * bar[t].close` for every bar — no commission/slippage modeling, since it's a comparison reference line, not a tradable strategy. It's wired into all three backtest result types identically: `execute_backtest` (single-ticker, `services/backtest_service.py`) and `execute_walk_forward` (`services/walk_forward_service.py`) call it directly over their respective `df`; `execute_portfolio_backtest` (`services/portfolio_backtest_service.py`) computes one per-ticker buy-and-hold curve per basket member and combines them via the same `aggregate_equity_curves` date-union-with-forward-fill helper already used for the portfolio's real equity curve. Each of the three result tables (`BacktestResult`, `PortfolioBacktestResult`, `WalkForwardBacktestResult`) has its own `benchmark_equity_curve` JSON column, and each of the three `get_*_detail`-style response builders includes it alongside the strategy's own `equity_curve` — the frontend's `BacktestChart.jsx` renders it as a second line via an optional `benchmarkEquityCurve` prop, wired up for single-ticker, portfolio, and walk-forward results alike.

### Market data import (`routers/data.py`)
All endpoints below are under `/api/data`, require auth, and have no ownership (any authenticated user can read/write any ticker's data — see Data models below). Three ways to write bars in, three to read them back, one to delete:
- `POST /upload` — single bar, JSON body (`MarketDataCreate`: `ticker`, `date`, OHLCV, optional `adj_close`).
- `POST /upload-csv` — bulk, multipart (`ticker` form field, optional — see below + `file`). Accepts two shapes, detected via `_split_bar_groups` by sniffing the file's first cell: a header'd `Date,Open,High,Low,Close,Volume[,Adj Close]`-style CSV (case/space-insensitive; `ticker` is required for this shape since the file doesn't carry one), or a headerless Stooq-style per-symbol export — one row per bar as `TICKER.COUNTRY,PERIOD,YYYYMMDD,HHMMSS,Open,High,Low,Close,Volume,OpenInt` (also accepts a `<TICKER>,<PER>,...` header row), first-cell-matched via regex against the `SYMBOL.COUNTRY` shape. For that shape the ticker is read off each row instead (country suffix after the first `.` stripped, e.g. `AAPL.US` → `AAPL`), so `ticker` is optional and a file spanning multiple symbols is split into one group per symbol, each upserted separately — the endpoint returns a single `{ticker, inserted, skipped}` dict for one group or a list of them for multiple.
- `POST /import/{ticker}` — bulk, fetches daily history from **Alpha Vantage** (`TIME_SERIES_DAILY`, `outputsize=full`) and imports it. Needs a real API key for any symbol beyond the demo one — see Environment above. This used to hit Stooq's free CSV export instead; Stooq now gates that endpoint behind a client-side JS proof-of-work challenge specifically to block scripted requests (confirmed by hand: a plain request gets an immediate 404, a browser-UA'd one gets the unsolvable challenge page instead of data), so it no longer works from a server-side client. Don't reintroduce Stooq scraping here without solving that — which would mean building bot-detection evasion — instead of just picking a documented API.
- `GET /tickers` — distinct tickers, alphabetical.
- `GET /{ticker}/range` — `{ticker, start_date, end_date, count}`, the min/max date and row count on file for a ticker; 404s if none. Used by the frontend to constrain a backtest's date pickers to a range that actually has data (see Frontend structure below).
- `GET /{ticker}/historical` — optional `start_date`/`end_date` query params, always ordered by date — mirrors the exact query `backtest_service.run_backtest` issues, so this doubles as a "preview what a backtest would load" endpoint.
- `DELETE /{data_id}` — single row.

`upload-csv` and `import/{ticker}` both funnel through the module-private `_bulk_upsert_market_data(ticker, df, db)` helper, which normalizes column names, requires `date/open/high/low/close/volume`, and skips any `(ticker, date)` pair already stored rather than erroring on the unique constraint — keep new bulk-import paths going through this helper rather than reimplementing insert/skip logic.

**Fixed:** `_bulk_upsert_market_data` used to parse the `date` column with a bare `pd.to_datetime(df["date"])`. That's fine for ISO-ish date strings, but a bare 8-digit `YYYYMMDD` value (as opposed to `"1984-09-07"`) — the shape both Excel and Stooq exports commonly use, e.g. `19840907` — has no explicit `format`, so pandas reads it as **nanoseconds since the Unix epoch** instead of a calendar date: `19840907` became `1970-01-01T00:00:00.019840907`, not `1984-09-07`. Every row in a YYYYMMDD-dated file landed within fractions of a second of 1970-01-01 instead of its real date; re-uploading the same (or an overlapping) file produced identical bogus timestamps, which the `(ticker, date)` dedup then matched exactly — surfacing as "0 bar(s) imported, N already on file" with no visible error, even though nothing was ever stored under the correct dates. Fixed via `_parse_bar_dates()`, which detects an all-8-digit column and parses it with `format="%Y%m%d"` explicitly; anything else still goes through plain `pd.to_datetime`. If you add another date-bearing import path, route it through `_parse_bar_dates` rather than calling `pd.to_datetime` directly — this is covered by `tests/test_data_import.py::test_bulk_upsert_parses_yyyymmdd_integer_dates`. Any `MarketData` rows already written under the bogus near-1970-01-01 timestamps from before this fix are stale and need manual cleanup (e.g. `DELETE FROM market_data WHERE date < '1970-01-02'`) — this fix does not retroactively repair already-stored rows.

### Async task execution (Celery + Redis)
Four request paths that used to run synchronously inline in a request handler now create a pending row/job, commit it, enqueue a Celery task via `.delay(...)`, and return immediately — the actual work happens later in a separate worker process: `POST /api/backtest/run` (`run_backtest_task` → `services/backtest_service.py::execute_backtest`), `POST /api/backtest/run-portfolio` (`run_portfolio_backtest_task` → `services/portfolio_backtest_service.py::execute_portfolio_backtest`), `POST /api/data/upload-csv` (`upload_csv_task` → `services/data_import_service.py::execute_csv_import`), and `POST /api/data/import/{ticker}` (`import_alpha_vantage_task` → `execute_alpha_vantage_import`). Each `execute_*` function is unchanged in its actual computation from the old synchronous version — only the calling convention moved. `BackEnd/tasks.py` holds every `@celery_app.task` definition; each is a thin sync wrapper that runs its async service function via a fresh `asyncio.run(...)` call (see `_run_with_session`), and `BackEnd/celery_app.py` configures the `Celery` app itself (broker URL, time limits, `task_always_eager` for tests).

**No Celery result backend.** `celery_app.py` sets `backend=None` — task status/output is never read back through Celery's own result-tracking machinery. Instead every task writes its outcome directly onto the row it was enqueued for (`BacktestResult.status`/`.error_message`, `PortfolioBacktestResult.status`/`.error_message`, `DataImportJob.status`/`.error_message`/`.result`), each moving `pending` → `running` → `success`/`failed`. Callers (the frontend, via polling `GET /api/backtest/{id}`, `GET /api/backtest/portfolio/{id}`, or `GET /api/data/jobs/{job_id}`) read status off the row, not off Celery. This is why every `execute_*` function's docstring promises "never raises" — a worker process has no HTTP response to raise an exception into, so every failure mode (bad strategy code, no market data, a provider HTTP error, a DB error) must be caught inside the function and recorded on the row; letting anything propagate out of `execute_*` leaves that row stuck at `status="running"` forever with nothing to ever flip it. Each of the four `execute_*` functions' catch-all `except Exception` block does `await db.rollback()` before setting `status`/`error_message` and committing (a DB-level failure can leave the session mid-failed-transaction, and committing straight into that would itself raise) and records `f"{type(e).__name__}: {e}"` rather than bare `str(e)` (some exceptions, e.g. Celery's `SoftTimeLimitExceeded`, stringify to `''`, which would otherwise leave `error_message` uninformative).

**Ownership-check-before-enqueue invariant.** `create_pending_backtest`/`create_pending_portfolio_backtest` run the full ownership chain walk (`strategy.project.owner_id != user.id`, eager-loaded per the existing pattern above) and commit the pending row *before* anything is enqueued — a task is only ever queued for a row that's already known to belong to the requesting user, since the worker that eventually executes it has no `user` in scope to check against. `upload_market_data_csv`/`import_market_data_from_web` don't have an ownership check to make (`MarketData` is unowned, see Market data import above) but follow the same create-row-then-enqueue shape.

**Fixed:** All four `.delay(...)` call sites (`routers/backtest.py`, `routers/data.py`) used to call `.delay(...)` unguarded right after committing the pending row. If the broker (Redis) is unreachable at that moment, `.delay()` raises, FastAPI turns the uncaught exception into a generic 500, and the already-committed row is left at `status="pending"` forever with nothing ever picking it up. Each call site now wraps `.delay(...)` in `try/except Exception`, and on failure sets the row's `status="failed"` + an `error_message` naming the enqueue failure, commits that, then raises `HTTPException(503, "Task queue unavailable, please try again")` — a distinct status from the 400/403/404 validation errors these endpoints already raise. Covered by `tests/test_backtest_ownership.py::test_run_backtest_endpoint_marks_row_failed_when_delay_raises` (monkeypatches `.delay` to raise and asserts the row fails + a 503, rather than mocking Redis itself).

**Fixed:** `import_alpha_vantage_task`'s retry-exhaustion handling used to be dead code. Celery's `Task.retry(exc=...)` **re-raises the original exception** once retries are exhausted — it does not raise `MaxRetriesExceededError` when `exc=` is passed (verified empirically against this project's installed Celery version, not just by reading its source) — so the task's old `except MaxRetriesExceededError: _mark_job_failed(...)` branch was unreachable; after the final retry, `httpx.ConnectError`/`httpx.TimeoutException` propagated straight out of the task uncaught and the `DataImportJob` row stayed `status="running"` permanently (the frontend then polled for its full timeout and reported a generic "Timed out" instead of the real reason). Fixed by checking `self.request.retries >= self.max_retries` explicitly before deciding whether to `raise self.retry(exc=exc)` or call `_mark_job_failed` directly. `max_retries` is `1` (exactly one retry, two attempts total — matches the stated retry policy; `max_retries=2` would have meant two retries, three attempts). Covered by `tests/test_celery_tasks.py::test_import_alpha_vantage_task_marks_job_failed_after_retries_exhausted`, which drives the two attempts explicitly via `Task.apply(..., retries=N)` rather than relying on `task_always_eager`'s `.delay()` to actually loop — it doesn't: under eager mode `self.retry()` raises `celery.exceptions.Retry` immediately instead of re-invoking the task body (eager mode has no broker to redeliver the message), so `apply(..., retries=0)` and `apply(..., retries=1)` are used to simulate what a real worker's initial attempt and broker-redelivered final attempt would each see.

**Fixed:** `execute_csv_import`/`execute_alpha_vantage_import` didn't actually satisfy their own "never raises" contract. `execute_csv_import` only caught `ValueError` around `_split_bar_groups`/`_bulk_upsert_market_data` (a `SoftTimeLimitExceeded` or a racy `IntegrityError` from the read-then-insert dedup would've escaped uncaught); `execute_alpha_vantage_import`'s `httpx.AsyncClient.get(...)` call had no exception handling at all. Both now have a catch-all `except Exception` around the risky section. `execute_alpha_vantage_import` specifically re-raises `httpx.ConnectError`/`httpx.TimeoutException` unchanged (`except (httpx.ConnectError, httpx.TimeoutException): raise`) before its catch-all, so those two keep propagating up to `tasks.py`'s retry logic above — every other `httpx.HTTPError` subtype (`RemoteProtocolError`, `ReadError`, etc.) is instead caught and recorded on the job directly. Covered by `tests/test_data_import.py::test_execute_csv_import_marks_job_failed_on_non_value_error`, `::test_execute_alpha_vantage_import_marks_job_failed_on_non_retryable_http_error`, and `::test_execute_alpha_vantage_import_lets_connect_error_propagate`.

**Fixed:** `worker_db.py`'s lazy post-fork engine **must** use `NullPool`. Each Celery task body runs inside its own `asyncio.run(...)` call (see `tasks.py`), which spins up a brand-new event loop per task; `asyncpg` connections are bound to the event loop they were opened on, so a *pooled* connection checked out on one task's loop and reused on the next task's (different) loop raises `RuntimeError: Task ... got Future ... attached to a different loop`. SQLite/`aiosqlite` tolerates this fine, so the dialect-sensitive eager-mode test suite never catches it — same class of gap as the raw-string-date bug documented above; it was reproduced against a real multi-task Celery worker run against Postgres. `worker_db.py` also builds its engine lazily on first use inside each forked worker child (never at import time), separate from `database/connection.py`'s module-level engine, because `asyncpg` connections don't survive `fork()` — reusing the API process's engine directly in a prefork worker is unsafe for the same reason.

**Fixed:** the Compose `worker` service's `command:` must invoke Celery as `uv run python -m celery -A tasks.celery_app worker ...`, not bare `uv run celery ...`. Celery's console-script entry point (unlike uvicorn's app-loader, which the `backend` service uses) doesn't add the working directory to `sys.path`, so `tasks.py`'s deferred `from services...` imports (each task imports its service function lazily, inside the task body, to avoid pulling `pandas`/heavy service deps into every worker fork at import time) fail with `ModuleNotFoundError`. Running via `python -m celery` instead puts the invocation's working directory on `sys.path` the same way any other `python -m` invocation does, which resolves it.

Tested in `tests/test_celery_app.py` (broker URL/`task_always_eager` env config — via `importlib.reload`, inherited test infra, not touched by this fix pass), `tests/test_connection_config.py` (unrelated `DATABASE_URL` fallback, same reload pattern), `tests/test_async_task_schema.py` (the new `status`/`error_message` columns on `BacktestResult`/`PortfolioBacktestResult` and the new `DataImportJob` table default to `pending`/`None` on creation), `tests/test_celery_tasks.py` (task bodies run end-to-end via `task_always_eager`, real in-memory `sqlite+aiosqlite` redirected in for `worker_db.get_worker_session_factory()`), and `tests/test_data_import.py`/`tests/test_backtest_ownership.py` (the router-level enqueue paths, including the `.delay()`-failure and non-`ValueError` regression tests above). No mocks beyond monkeypatching `httpx.AsyncClient.get`/`.delay` itself, consistent with this repo's real-execution testing style.

- `src/api/*.js` — one module per backend resource, thin axios wrappers around the shared `client.js` (base URL from `VITE_API_BASE`, JWT injected via `setAuthToken`). `src/api/data.js` covers the `routers/data.py` endpoints above.
- `src/state/AuthContext.jsx` — the only global state; holds the JWT and exposes `login`/`register`/`logout`.
- `src/components/ProtectedRoute.jsx` — gates routes on `useAuth().isAuthenticated`; used in `App.jsx` for `/projects`, `/data`, `/projects/:projectId/strategies`, `/strategies/:strategyId/backtest`.
- Page components under `src/pages/` correspond 1:1 with those routes. `DataPage.jsx` (`/data`) is the market-data-import UI (CSV/TXT upload + Alpha Vantage import, the latter's API key entered in the UI and persisted client-side in `localStorage` under `quanttrade_alpha_vantage_api_key` — not sent anywhere but this app's own backend). Its upload form's ticker field is optional (`api/data.js`'s `uploadMarketDataCsv` only appends it to the multipart body when non-empty) since `POST /upload-csv` infers it from Stooq-style `.txt` files — see Market data import above; the result panel renders either the single-ticker response or, for a multi-symbol `.txt` upload, one line per per-ticker result in the returned array. `StrategiesPage.jsx`'s backtest form sources its ticker `<select>` from `GET /api/data/tickers` and constrains the start/end date `<input type="date">` `min`/`max` from `GET /api/data/{ticker}/range`, so the UI can't submit a range with no underlying data.

**Data is assumed daily.** `DataPage.jsx`'s two upload cards and `StrategiesPage.jsx`'s ticker/date-range hint all display a static "daily bars" indicator (a `.chip` in the card headers, and "N daily bars" in the bar-count text). If per-ticker frequency detection is ever added, it needs a real backend field first; don't infer it client-side from bar spacing without discussing where that logic should live.

**Fixed:** `src/styles.css`'s global `input, textarea, select` rule sets `color: var(--fg)` (light text) for the closed `<select>` control, which reads fine against its own near-transparent dark background. But `background` set on a `<select>` doesn't carry into the browser's native opened-option-list popup (Chrome/Edge fall back to a default white popup background), while `<option>` still inherits the light `--fg` text color — so every dropdown's open state rendered white-on-white. Fixed with an explicit `select option { background: #10141f; color: var(--fg); }` rule. If you add another themed form control whose popup/native rendering is separate from its closed state (e.g. `<datalist>`), check the opened state specifically rather than just the closed control.

### Data models (`BackEnd/database/models.py`)
`User` 1—N `Project` 1—N `Strategy` 1—N `BacktestResult`. `Strategy` also has a parallel 1—N `PortfolioBacktestResult` (see Portfolio-level backtests above) — same ownership chain, walked the same way. `MarketData` is independent (keyed by `ticker`+`date`, unique-constrained), not owned by a user — it's shared reference data that any authenticated user can query/upload/delete via `routers/data.py`. `BacktestResult` stores `results` (metrics), `trades`, `signals`, and `equity_curve` as JSON columns; `PortfolioBacktestResult` stores `allocations`, `results` (pooled metrics), `equity_curve` (aggregate), and `per_ticker` (each ticker's own `results`/`trades`/`signals`/`equity_curve`, same shape as a single-ticker result) as JSON columns. There's no migration tooling (`init_db()` only runs `Base.metadata.create_all`, which won't alter an existing table) — if you add/change columns, the local dev DB's tables need to be dropped and recreated manually; a purely additive new table (like `PortfolioBacktestResult`) just needs a backend restart, `create_all` fills in the missing table without touching existing ones. The `status`/`error_message` columns on `BacktestResult`/`PortfolioBacktestResult`, plus the `DataImportJob` table, are schema changes added for async task execution — any pre-existing local/dev Postgres database predating this needs those tables dropped and recreated (or `docker compose down -v` for a fresh volume); `create_all` adds the new `DataImportJob` table for free but silently leaves the two existing tables without their new columns, which then 500s the first time code tries to read/write `status`/`error_message` on a row from either. The `allow_short`/`stop_loss_pct`/`take_profit_pct` columns added to both `BacktestResult` and `PortfolioBacktestResult` for shorting/stop-loss/take-profit support are the same kind of additive-but-not-migration-safe change — a pre-existing local/dev Postgres database needs those two tables dropped and recreated (or a fresh volume) the same way, or reads/writes of those columns on an old row will 500. The new `WalkForwardBacktestResult` table (see Walk-forward backtests above) is purely additive — `create_all` fills it in on restart like `PortfolioBacktestResult` was — but the `benchmark_equity_curve` columns added to both `BacktestResult` and `PortfolioBacktestResult` for the buy-and-hold overlay are the same kind of unsafe change as `allow_short`/`stop_loss_pct`/`take_profit_pct` above, with a sharper failure mode: `execute_backtest`'s `record.benchmark_equity_curve = benchmark_curve` assignment (`services/backtest_service.py`) happens *outside* its `try/except` block's protection — the assignment itself can't raise (it's just a Python attribute set on the ORM instance), but the `await db.commit()` immediately after it will raise on a pre-existing DB missing the column, which breaks the **existing, previously-working** single-ticker backtest flow entirely (every run ends `status="failed"`) until the table is recreated or the column added — not just the new walk-forward feature. Same underlying risk applies to `PortfolioBacktestResult.benchmark_equity_curve` in `execute_portfolio_backtest`.
